# 第 9 章 让插件独立开发

## 9.1 独立开发是什么意思

“插件可以独立开发”不只是“代码放在另一个文件夹”。真正的独立，是指作者不需要主程序的全部源码，也不需要每次启动整个主程序，就能写完、跑通、验证一个插件。

要做到这一点，三样东西必须从主程序里拿出来：接口头文件、一个能加载插件的假宿主、一套能自动跑的测试。

接口头文件如果只在主程序源码里，作者得把整个主程序下载下来。假宿主如果没有，作者每次调试都得启动完整软件，慢且不稳定。测试如果不能自动跑，每次改完只能靠手点，迟早漏掉。

## 9.2 把接口头文件单独放

现在 `plugin_api.h` 在宿主项目里。插件要引用它，得把路径写死，或者复制一份。复制会让两个版本漂移，改了宿主忘了改插件，编译出来的东西对不上。

正确的做法是把头文件做成一个独立的小包，目录结构大概是这样：

```text
sdk/
  include/
    plugin_api.h
  README.md
  VERSION
```

宿主和插件都引用这个目录。宿主编译时加 `-I../sdk/include`，插件也加同样的路径。这样只有一份头文件，改一处两边都生效。

`sdk` 里只放“双方都同意的东西”：接口声明、结构体定义、常量、版本号。不放实现，不放只有宿主才需要的内部类型。这个目录就是第 4 章说的“合同”。

真实项目里，`sdk` 可以单独打成一个压缩包，带版本号发布。插件作者下载 `sdk-1.2.0.zip`，解压后就能编译。宿主升级接口时，发布新的 `sdk`，插件按需升级。

## 9.3 假宿主

假宿主是一个很小的程序，它实现 `PluginApi`，加载指定插件，把插件注册的命令打印出来。它不启动界面，不读配置，不连接网络，只验证“插件能不能被加载、能不能注册”。

```cpp
#include "plugin_api.h"
#include <cstdio>
#include <string>

#ifdef _WIN32
#include <windows.h>
#define LIB_OPEN(p) LoadLibraryA(p)
#define LIB_SYM(h, n) ((void*)GetProcAddress(h, n))
#else
#include <dlfcn.h>
#define LIB_OPEN(p) dlopen(p, RTLD_NOW)
#define LIB_SYM(h, n) dlsym(h, n)
#endif

static void on_command(const PluginCommand* cmd) {
    std::printf("  命令: %-10s %s\n", cmd->name, cmd->help ? cmd->help : "");
}

static void on_log(const char* message) {
    std::printf("  日志: %s\n", message ? message : "");
}

int main(int argc, char** argv) {
    if (argc < 2) {
        std::printf("用法: mock_host <plugin.dll>\n");
        return 1;
    }

    auto handle = LIB_OPEN(argv[1]);
    if (!handle) {
        std::printf("加载失败: %s\n", argv[1]);
        return 2;
    }

    auto init = (int(*)(const PluginApi*))LIB_SYM(handle, "plugin_init");
    if (!init) {
        std::printf("缺少 plugin_init\n");
        return 3;
    }

    PluginApi api{};
    api.size = sizeof(PluginApi);
    api.version = PLUGIN_API_VERSION;
    api.register_command = on_command;
    api.log_info = on_log;

    std::printf("加载 %s\n", argv[1]);
    int rc = init(&api);
    std::printf("init 返回 %d\n", rc);
    return rc;
}
```

这个程序不到六十行，但它给了插件作者一个完整的验证环境。编译出插件后，直接 `mock_host my_plugin.dll`，就能看到注册了哪些命令、初始化有没有报错。

假宿主不追求和真宿主一模一样。它只覆盖接口承诺的行为。真宿主的内部实现、界面细节、配置读取，都不属于合同，也不应该在插件的单元测试里依赖。

## 9.4 自己写一个测试框架

C++ 没有自带测试框架，但写一个最小的不难。

```cpp
#include <cstdio>

static int g_failed = 0;

#define CHECK(condition)                                                  \
    do {                                                                  \
        if (!(condition)) {                                               \
            std::printf("FAIL %s:%d  %s\n", __FILE__, __LINE__, #condition); \
            ++g_failed;                                                   \
        }                                                                 \
    } while (0)

static int add(int a, int b) { return a + b; }

int main() {
    CHECK(add(2, 3) == 5);
    CHECK(add(-1, 1) == 0);
    CHECK(add(0, 0) == 0);
    std::printf("%s\n", g_failed == 0 ? "全部通过" : "有失败");
    return g_failed == 0 ? 0 : 1;
}
```

`#define CHECK(...)` 定义一个宏。宏在编译前展开，把一段代码原样插到调用的地方。

`do { ... } while (0)` 是一个常用技巧。它把多条语句包成一个整体，展开后可以安全地放在 `if` 后面，不会因为分号出问题。

`__FILE__` 和 `__LINE__` 是编译器提供的宏，分别展开成当前文件名和行号。测试失败时，能直接定位到哪一行。

`#condition` 里的 `#` 是“字符串化”：把宏参数原样变成字符串。`CHECK(a == b)` 失败时，打印出来的就是 `a == b`，不用再手写说明。

`g_failed` 记录失败次数。主函数最后根据它返回 0 或 1，自动检查通过退出码判断成败。

这个框架只有十几行，够用了。等测试多起来，可以换成 Catch2 或者 GoogleTest，但那是以后的事。

## 9.5 本地联调

插件开发过程中，有三种跑法，耗时依次增加。

**只跑测试。** 改完代码，编译测试程序，运行。几百毫秒出结果。适合验证纯逻辑，比如命令解析、字符串处理、数据计算。

**用假宿主跑。** 编译出动态库，用 `mock_host` 加载，看注册和初始化。几秒出结果。适合验证接口对接，比如命令有没有注册上、日志有没有输出。

**装进真宿主。** 把动态库复制到主程序的 `plugins` 目录，启动主程序，手动点一遍。分钟级。适合最终验收。

三种跑法都要有，不能只有最后一种。只有最后一种，开发一个插件要反复启动完整软件，效率很低。

本地联调时，动态库经常被占用。Windows 上，一个加载中的 DLL 不能覆盖。改完代码重新编译，可能报“无法写入文件”。解决办法是先关闭宿主，或者编译到另一个文件名，再替换。

Linux 上通常可以直接覆盖正在使用的 `.so`，因为文件被替换后，已经打开的进程仍然指向旧文件，新进程用新文件。这个差异在跨平台开发时会遇到。

## 9.6 持续集成

插件作者可以在每次提交后自动跑一遍检查。GitHub 提供免费的自动构建服务，配置文件放在 `.github/workflows/ci.yml`。

```yaml
name: build

on: [push, pull_request]

jobs:
  linux:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: cmake -B build -DCMAKE_BUILD_TYPE=Release
      - run: cmake --build build
      - run: ctest --test-dir build --output-on-failure

  windows:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - run: cmake -B build
      - run: cmake --build build --config Release
```

`yaml` 是一种用缩进表示层级的配置格式。这段配置的意思是：每次有人提交代码，就在 Linux 和 Windows 各启动一台机器，检出代码、配置、编译、跑测试。

`on: [push, pull_request]` 表示触发条件：推送代码或者发起合并请求。

`runs-on` 指定操作系统。两个任务并行跑，任何一个失败都会在页面上标红。

`cmake -B build` 在 `build` 目录生成构建文件。`cmake --build build` 执行编译。`ctest` 跑测试。

CI 的价值在于“在别人的机器上也能编译”。你本地能过，不代表别人能过。不同编译器、不同标准库版本、不同路径分隔符，都会暴露问题。

## 9.7 版本与依赖

插件和宿主之间的版本关系，要在清单里写清楚。

```json
{
  "name": "hello",
  "version": "1.2.0",
  "api": 1,
  "requires": {
    "host": ">=1.0.0 <2.0.0"
  }
}
```

`api` 是接口版本，对应 `PLUGIN_API_VERSION`。`requires.host` 是宿主版本范围。

宿主加载时检查这两项。`api` 不等于当前版本，直接拒绝；宿主版本不在范围内，也拒绝，并提示用户升级。

插件之间也可能有依赖。比如一个“云同步”插件依赖“存储”插件提供的服务。清单里可以写：

```json
{
  "requires": {
    "host": ">=1.0.0 <2.0.0",
    "plugins": ["storage"]
  }
}
```

宿主要在加载前检查这些插件在不在，不在就跳过，并给出提示。加载顺序要按依赖排，第 10 章会讲。

版本号用三个数字，主版本加一表示不兼容，次版本加一表示增加功能但兼容，修订号加一表示修 bug。这个约定叫语义化版本，插件和宿主都遵守，用户才能一眼看出升级会不会出问题。

## 9.8 插件作者的日常

把上面的东西合起来，一个插件作者的日常大概是这样。

拉取 `sdk`，用生成器创建插件骨架。改 `plugin.cpp`，加自己的命令。跑 `cmake --build`，编译。跑 `mock_host`，看注册结果。写几个 `CHECK`，验证逻辑。提交，CI 自动跑 Linux 和 Windows。打标签，发布新版本。

整个过程不需要主程序的源码，也不需要主程序团队配合。这就是“独立开发”的实际含义。

下一章讨论插件做完之后怎么到达用户手里。打包、签名、安装、更新，这几步决定了插件生态能不能持续运转。
