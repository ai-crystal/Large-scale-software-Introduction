# 第 10 章 结构要付多少代价

## 10.1 每一层都要花钱

前九章介绍了不少结构。每一项都能解决一类问题，也都要付出代价。

代价分几种。

**通信代价。** 跨进程调用比函数调用慢。序列化、传输、反序列化，每一层都要时间。

**内存代价。** 每个进程有固定开销，每个服务有一份实例，每个插件有一份上下文。

**启动代价。** 进程创建、动态库加载、插件初始化，都要时间。

**认知代价。** 插件作者要理解更多的概念。接口从三个函数变成十几个，文档从两页变成二十页。

**调试代价。** 跨进程的问题要在多个进程之间对照，出错时的堆栈可能不完整。

这些代价不是均摊的。有些结构几乎不花钱，有些很贵。

判断贵不贵，靠的不是感觉。下面四笔账都可以算，也都可以测。

## 10.2 通信账

通信成本有三个台阶，每个台阶差三个数量级左右。

| 调用方式 | 一次耗时 | 一帧 16.7 毫秒内能做多少次 |
|---|---|---|
| 同进程直接或虚函数调用 | 几纳秒到十几纳秒 | 百万量级 |
| 经过服务代理（查表加转换） | 几十纳秒 | 十万量级 |
| 跨进程小消息往返 | 几十微秒 | 几百次 |
| 跨进程带一兆数据 | 毫秒级 | 十几次 |

三行的差距不是实现优劣，是物理距离。同进程调用只动几个寄存器和缓存，跨进程要把数据从用户态交给内核、唤醒另一个线程、等它被调度、再把结果送回来。两次调度本身就占几十微秒，剩下的是拷贝。

“一帧能做多少次”这列是最实用的换算。如果某个接口在每帧的循环里调，而这个接口是跨进程的，预算就只有几百次。三千个图元一个一个跨进程提交，必然掉帧，不管代码写得多漂亮。

测一次只要几行。

```cpp
volatile long long sink = 0;
auto t0 = std::chrono::steady_clock::now();
for (int i = 0; i < 100000; ++i) sink += bench_once();
auto dt = std::chrono::steady_clock::now() - t0;
long long us = std::chrono::duration_cast<std::chrono::microseconds>(dt).count();
printf("%.2f us/次\n", us / 100000.0);
```

三个容易测错的地方。没有 `volatile` 或者结果没被用，整个循环会被编译器删掉，测出零点几微秒；用了平均值而不是中位数，一两个毛刺就能把结论拉偏；连续测太多次，CPU 降频，后面几轮变慢。

测出来偏慢也不必急着优化。先看能不能批量，把一千次小调用合成一次大调用，往返成本只付一次，剩下的成本随字节线性增长，比往返便宜得多。大多数“跨进程太慢”的情形，实际上都是“调用太碎”。

## 10.3 内存账

内存比时间难算，因为它有四个来源，而且其中最大的一个经常被忽略。

**进程固定开销。** 一个空进程在桌面系统上要占几十兆，包含运行时、堆预留和加载的系统库。这部分与插件大小无关。

**库加载。** 每个进程加载自己的依赖，图形栈、脚本引擎、网络库各几兆到几十兆。

**服务实例。** 每个服务一份状态，从几 K 到几兆不等。索引类服务往往很大。

**上下文与缓冲。** 每个插件一份上下文、日志缓冲、命令缓冲，每项几 K 到几 K 的几倍。

四个来源里，第一项和二项是乘法。把二十个插件拆成二十个进程，固定开销和库开销各乘二十，内存涨得比想象中快。这也是“分组同进程”的真正理由，不只是为了速度。

自测方法很直接。跑一次全部同进程的版本，记下峰值内存；再跑一次全部独立进程的版本，记同一个值。差值就是隔离的内存价格。测的时候看专用工作集，别把共享页重复计入，否则二十个进程会把同一份系统库算二十次。

一个具体的例子。五个插件原本同进程，总共二百多兆。改成各自一个进程之后，每个进程都要加载一套图形栈，单进程四十兆，五个就是两百兆，总数奔到四百多兆。如果这些插件都是画界面的，那这套图形栈就加载了五遍。

## 10.4 启动账

启动要用的人能感知，所以得拆开算。一次冷启动至少四段。

![图 10-1　冷启动的四段，每段的时间量级差一个级别](../images/10/fig10-1-boot.png)

**进程创建。** 几十毫秒。创建子进程、初始化运行时、建消息队列都在这里。

**动态库加载与符号解析。** 看依赖，几十到上百毫秒。图形栈和大型运行时是主要开销。

**插件初始化。** 每个插件几毫秒。读配置、注册命令、建连接。

**首帧渲染。** 看界面复杂度，几十到上百毫秒。

四段相加就是用户感知的等待。全同进程的时候，前两段只付一次；拆成多进程之后，前两段按组付。

测的时候不要只记总时长，分段打点。

```cpp
using clk = std::chrono::steady_clock;
auto t0 = clk::now();
Handle h = open_library(path);
auto t1 = clk::now();
int rc = init(api);
auto t2 = clk::now();
log("lib %lldms init %lldms rc=%d", ms(t1 - t0), ms(t2 - t1), rc);
```

分段之后优化就有地方下手了。库加载慢就做懒加载，init 慢就看是不是在里面做了网络请求，进程创建多就合并进程。没分段的时候只有一个“启动慢”，只能猜。

冷启动和热启动要分开看。热启动有文件缓存，库加载可能只有冷启动的三分之一。给用户报的数字应该是冷启动，因为安装完第一次打开就是冷的。

## 10.5 认知账用什么量

认知代价听着虚，但有四个可以数的指标。

**概念数。** 写一个最小插件需要理解多少个名词。只有命令和事件两个；加上契约版本、权限、服务、能力协商就是六个。新人每多一个概念，就多一块需要建立心智模型的东西。

**最小可用代码量。** 一个能跑的插件要写多少行，清单里有多少必填字段。必填字段从两个涨到八个，配错的可能就成倍上升。

**上手时间。** 找一个没接触过的人，只给文档，让他写一个把当前文件路径打到日志的插件。计时，并记下他卡在哪一步。这个实验比任何问卷都准，而且能直接暴露文档缺口。

**示例覆盖。** 每种能力是不是都有一个可以直接跑的最小示例。文档里只有函数签名没有示例的能力，实际使用率往往很低。

四个指标里，上手时间最有说服力。一个下午就能写出第一个插件的系统，和一个要读两天文档才能跑起来的系统，第三年时的插件数量差距会很大。

控制认知代价不靠缩功能，靠分层。最小插件只写三个函数就能跑，需要事件时加事件，需要服务时加服务。所有能力都是可选加载，不需要的部分在文档里也不占位置。

四个指标值得半年测一次。同一个插件，同样的文档，重新计一次时，发现上手时间从一下午变成两天，那就是接口在变复杂的明确证据，不用等用户抱怨。这个数字比代码行数可靠，因为它把文档、示例、错误信息全包进去了。

## 10.6 调试代价是前三笔的利息

调试成本不独立，它是前三笔的衍生费用，很容易被漏算。

同一个 bug，同进程时一份堆栈就能定位；跨进程时要对照两个日志，堆栈跨不过进程边界，只能靠消息 ID 把两边的记录串起来。偶发的问题还得先把时序复现出来，而时序问题一旦涉及调度，复现概率就不可控。

一笔可以估的账。一次跨进程偶发故障，平均定位时间从半小时变成一两天。一年遇到五次，就是十个工作日。对比一下买隔离花了多少内存、多少启动时间，这笔账经常是最贵的。

降低这笔账不靠少用进程，靠可观测性。每个跨进程调用带一个请求 ID，两边的日志都打上这个 ID，一条命令就能把一整次调用串起来。这一条做了，调试成本能降一大截，比把超时从三秒改到一秒有用得多。

## 10.7 便宜的结构

**命令表。** 一次哈希表查找，微秒级。加一层 `owner` 字段几乎不花钱。

**事件总线。** 每个事件遍历一次订阅者列表，几十微秒。除非频率极高（每帧几百次），否则感觉不到。

**扩展点容器。** 和命令表一样，查表开销可以忽略。

**版本检查。** 加载时做一次，之后不再检查。开销在启动阶段，占比很小。

这几项的共同点是只在“结构性操作”时发生，也就是注册、查找、加载。这些操作频率低，开销可以接受。

## 10.8 中等的结构

**钩子链。** 每次保存要遍历所有钩子，每个钩子处理一遍内容。如果内容是几兆的文本，遍历五遍就是几兆的五次复制。

优化方式是把多个钩子合并。能一次遍历完成的，不要分开做；能原地修改的，不要复制。

**服务代理。** 每次调用查一次表，再加一次类型转换。几十纳秒，比直接调用慢一点，但远不到能感觉到的程度。

**能力协商。** 每次查询一次特性表，字符串比较。如果放在热路径上，会变成瓶颈。做法是在初始化时查一次，结果缓存起来。

## 10.9 昂贵的结构

**跨进程调用。** 一次往返几十微秒到几毫秒，取决于数据大小和平台。

这个数量级意味着每秒最多几千次跨进程调用。超过这个频率，就要考虑同进程或者批处理。

**进程启动。** 几十到几百毫秒。用户如果点了按钮要等半秒以上，体验明显变差。

做法是懒加载加预热。常用插件在启动时预加载，不常用的第一次用到时再加载；加载过程中显示进度。

**大量插件同时加载。** 每个插件初始化几毫秒，一百个插件就是几百毫秒。如果每个都开一个进程，可能几秒。

做法是并行加载加分组。能同进程的放一起，独立进程的并行启动。

## 10.10 算一笔具体的账

假设一个编辑器，二十个插件，其中五个第三方。

**同进程方案。**

- 启动：二十个插件各 3 毫秒 = 60 毫秒
- 内存：一个进程约 200 兆，加插件共 260 兆
- 命令调用：纳秒级
- 崩溃影响：任意插件崩溃导致应用退出

**混合方案。**

- 启动：十五个内置 45 毫秒，五个第三方各 80 毫秒并行 = 约 125 毫秒
- 内存：宿主 260 兆，五个插件进程各 40 兆 = 460 兆
- 命令调用：内置纳秒级，第三方几十微秒
- 崩溃影响：内置插件崩了应用退出，第三方崩了只损失那个插件的功能

多花了 200 兆内存和 65 毫秒启动时间，换来的是“第三方插件崩溃不会带走用户数据”。

对一个要长期运行的编辑器来说，这笔交易通常划算。对一个几秒钟就用完的命令行工具来说，不划算。

## 10.11 三个约束定下选型

前面几节把成本算清楚了。真正做决定的时候，不用把所有数字加起来比总分，只看三个硬约束。

**内存上限。** 产品要跑到低端设备上，可用内存可能只有一两百兆。这种情况下，把二十个插件拆成二十个进程直接出局，没得讨论。

**启动预算。** 用户打开一个编辑器可以等一秒，打开一个命令行工具只愿意等一百毫秒。前者允许懒加载和预热，后者只能一次性同步加载。

**崩溃容忍。** 插件崩了会丢用户没保存的内容，还是只少一个按钮。前者必须有隔离，后者可以省。

三个约束先写成三个数字，再选结构。

| 约束 | 紧的时候的选择 | 松的时候的选择 |
|---|---|---|
| 内存 | 全部同进程，分组只按依赖 | 按信任分组，一组一个进程 |
| 启动 | 同步加载，只带必需插件 | 懒加载加后台预热 |
| 崩溃容忍 | 第三方全部独立进程加自动重启 | 只靠 try/catch |

三个约束常常互相矛盾。内存紧和崩溃容忍高就是一对冤家，一个要求合，一个要求分。这时候要做的是分类，把需要隔离的插件缩到最小范围，比如只把处理网络和解析不可信文件的那几个拆出去，其余同进程。

约束写成数字还有个好处，项目后期加结构时，可以直接对照这三个数字否掉不合理的提议。“把所有插件都改成独立进程”在内存紧的产品上，不需要讨论架构哲学，直接算一下多花多少兆就够了。

三个约束每年重算一次。产品从桌面搬到网页，或者从高端机型扩到低端机型，之前合理的答案会变得不合理。

## 10.12 一次可以自己做的对照实验

前面四笔账的量级都是从别处抄来的。换成自己的程序，数字会不一样，所以值得自己测一次。

准备两份构建。同一个插件，一份同进程加载，一份在独立进程里跑，其余代码完全一致。用 Release，不要用 Debug。Debug 下的开销往往是 Release 的三到五倍，测出来的比例没有参考价值。

跑同一组操作。打开十个文件、保存五次、滚动两屏、关掉。手动做也行，脚本驱动更一致。

记四个数字。从点图标到界面可操作的时间；峰值专用工作集；一次典型插件回调的耗时；杀掉插件进程之后恢复到可用状态的时间。

每个数字测三次冷启动，取中位数。第一次通常比其他两次慢很多，那是文件缓存还没热。

结果怎么读，取决于上一节那三个约束。

如果内存多了一百兆，启动多了一百毫秒，而崩溃恢复从“整个应用退出”变成“界面还在、少一个功能”，那这笔交易就很划算。如果产品要跑在只有两个 G 内存的办公机上，而插件只是画个图标，那就不划算。

如果跨进程之后每帧回调从几微秒变成几毫秒，说明这个插件的接口调得太碎，应该先改接口而不是放弃隔离。这个区分很重要，很多时候“隔离太慢”的真实原因是接口设计没考虑过跨进程。

最后一次实验不能覆盖全部情形。它只告诉你一个插件、一组操作下的价格。但价格的数量级是可以外推的，只要你不把结论推到完全不同的插件类型上。

实验记录下来，以后就不用重测。一张小表四列就够，插件名、部署方式、启动时间、峰值内存。里面条目多了，会发现一个规律，真正决定内存在哪里的是依赖库，而不是插件代码本身。两个看起来完全不同的插件，只要都依赖图形栈，内存开销就差不多。

这也解释了为什么“插件都很小，拆成进程应该不贵”这个直觉经常错。贵的不是插件，是每份进程里重复加载的那套基础设施。

四个数字里最容易被误读的是启动时间。测出来的启动变慢，未必全是隔离造成的，也可能是因为独立的插件进程在启动时会各自初始化一份日志和配置，而这些在同一个进程里本来就是共享的。看分段打点的结果，才知道慢在哪一段。

## 10.13 认知代价

这一项最难量化，但影响最大。

插件作者要理解的东西，从“写三个函数”变成“理解契约版本、扩展点形态、服务依赖、权限模型”。

插件少的时候，作者可以边看示例边写。插件多、生态大的时候，作者可能是第三方，看不到宿主源码，只能靠文档。

文档每多一页，愿意写插件的人就少一些。这句不是夸张，因为第三方的插件作者是拿了文档就走的，没有人给他解释。他卡在第一步就不写了，你甚至不会收到任何反馈，只会看到生态长不大。

控制认知代价的几个做法。

**默认简单。** 最简单的插件只写三个函数，不声明任何权限，不改任何配置，也能跑起来。

**渐进复杂。** 需要事件时加事件，需要服务时加服务，不需要的部分完全不出现。

**示例齐全。** 每种能力配一个最小示例，复制就能跑。

**错误友好。** 插件写错时报清楚的错误，指出缺什么、该怎么补。

## 10.14 什么时候不该加结构

前面几章介绍的结构，不是每个项目都需要。

**插件少于五个。** 冲突靠人工协调，事件顺序靠约定，不需要版本管理。

**插件全由自己团队开发。** 不需要权限模型，不需要签名，不需要独立进程。

**产品形态还在变。** 接口每周都改，现在定契约等于把不稳定的东西固化。

**性能是唯一指标。** 每帧的预算只有几毫秒，任何间接调用都要慎重。

**没有第三方。** 所有插件都是内置的，那它们其实就是模块，用普通的分层和构建就够。

判断标准就是第 1 章那句话，**结构跟着变化走。** 没有变化的地方加结构，只是给自己添麻烦。

## 10.15 一个粗略的判断表

| 情况 | 需要的结构 |
|---|---|
| 3 个内置插件，功能稳定 | 命令表 + 简单事件 |
| 10 个插件，有第三方 | 加契约版本、权限、独立进程 |
| 50 个插件，公开生态 | 加命名空间、服务注册、签名、审核 |
| 插件需要自定义渲染 | 加句柄、命令缓冲、图层 |
| 插件需要跨机器 | 加 RPC、序列化、认证 |

表格只是参考，具体项目要按自己的情况调整。判断的核心永远是一个问题，这个结构解决的问题现在真的发生了吗。

## 10.16 代价换来什么

最后回到最开始的那个问题，为什么要付这些代价。

因为不付的代价更高。

一个没有版本管理的插件系统，每次升级都会有一批插件失效，用户抱怨，作者流失。

一个没有隔离的插件系统，一个恶意插件就能拿走用户的全部数据。

一个没有服务注册的插件系统，插件之间靠事件喊话，代码绕、难调试、容易死锁。

这些代价不会立刻出现，但会在用户规模上来之后集中爆发。到那时再改，成本比一开始就做高得多。

所以结构的价值不在于“看起来专业”，而在于**把未来的问题提前解决**。前提是这些问题真的会来。下一章讨论怎么判断这一点。
