# 第 9 章 把结构装回去

## 9.1 前八章留下的零件

把前八章的决定列出来。

**内核。** 保留生命周期、服务注册、事件分发、资源与权限。不包含任何业务逻辑。

**扩展点。** 三种形态（列表、管道、单点），声明式和命令式两种提交方式，统一的标识规范。

**契约。** `size` 保证结构兼容，版本号保证语义兼容，能力协商处理细粒度特性。

**事件与钩子。** 订阅者分观察者、修改者、拦截者三类，顺序由优先级和显式依赖共同决定，短路要记日志。

**进程模型。** 按信任级别分组，内置插件同进程，第三方插件独立进程。

**服务注册表。** 命名空间隔离，支持必需依赖和可选依赖，跨进程用代理。

**渲染服务。** 句柄管理资源，命令缓冲提交绘制，图层隔离插件。

这些零件分开看都清楚，装在一起会有新的问题。这一章处理装的过程。

## 9.2 启动顺序

启动顺序决定了哪些东西必须比哪些东西早存在。

```text
1. 创建内核对象（注册表、总线、服务表、资源管理器）
2. 加载宿主自己的内置命令和内置服务
3. 扫描插件目录，读取清单
4. 按依赖关系排序
5. 逐个加载插件，调用 plugin_init
6. 事件总线开始接受事件
7. 进入主循环
```

几个容易出错的地方。

**第 2 步不能省。** 宿主自己的命令要在插件之前注册，否则插件注册的命令名可能和宿主冲突，宿主反而被拒绝。

**第 5 步要容错。** 一个插件初始化失败，跳过它，继续下一个。失败的插件留下的注册要清理干净。

**第 6 步有边界。** 插件加载过程中可能已经发了事件，但此时总线还不完整。稳妥的做法是加载阶段把事件缓存，加载完再统一分发。

## 9.3 启动阶段暴露的三个故障

启动顺序写对了不代表启动没问题。下面三个都是装配阶段的典型故障。

![图 9-1　启动阶段的先后关系，排序之后的每一步都必须能回滚](../images/09/fig9-1-boot.png)

**宿主命令被插件抢注。** 一个插件注册了 `help`，它想提供更详细的帮助。宿主的内置 `help` 在第 2 步注册，本该先占位。但如果开发时把第 2 步和第 5 步写反了，插件先到，内置命令被拒。表面上宿主少了一个命令，实际上插件拿到了宿主的名字，用户输入 `help` 看到的是插件的内容。

**加载阶段的事件丢了。** 插件在 `plugin_init` 里发一条 `document.opened`，想通知别人自己已经就绪。此时总线还没开，事件进了空列表，没有任何人收到，也没有任何报错。表现是“插件启动了但不工作”，查半天发现靠的是别人发事件才动。

缓存的写法要小心。把所有加载期事件存起来一次分发，听起来完整，实际上会把一批已经过期的事件冲给所有人。用户看到界面闪几下，插件被自己的旧事件淹了。比较稳的做法是只缓存“状态型”事件并在分发前合并，同类型的只保留最后一条。

**失败的插件留下了半成品。** `plugin_init` 返回失败，宿主关掉了库，却忘了擦掉前面已经注册的命令。注册表里留着一个函数指针，指向已经被卸载的代码段。用户输入那个命令，地址已经不在内存里。

```cpp
bool Host::load_plugin(const Manifest& m) {
    Handle h = open_library(m.path);
    if (!h) return false;
    InitFn init = (InitFn)resolve(h, "plugin_init");
    if (!init) { close_library(h); return false; }

    bool ok = false;
    try { ok = init(api_for(m.id)) == 0; }
    catch (...) { ok = false; }              // 插件的异常不能传出宿主

    if (!ok) {
        unregister_all(m.id);                // 关键一步，把半成品擦干净
        close_library(h);
        log_error("插件初始化失败，已回滚：" + m.id);
        return false;
    }
    loaded_[m.id] = h;
    return true;
}
```

把 `unregister_all` 写在失败分支里容易漏，因为“成功路径”很容易写完整，“失败路径”只想着关库。用作用域守卫更保险，让清理跟着离开函数走。

## 9.4 依赖排序

插件之间有依赖时，加载顺序不能随意。

拓扑排序的写法。

```cpp
std::vector<Manifest> sort_by_dependency(const std::vector<Manifest>& plugins) {
    std::map<std::string, const Manifest*> by_id;
    for (const auto& p : plugins) by_id[p.id] = &p;

    std::vector<Manifest> result;
    std::map<std::string, int> state;   // 0 未访问，1 访问中，2 完成

    std::function<void(const Manifest&)> visit = [&](const Manifest& p) {
        int& s = state[p.id];
        if (s == 2) return;
        if (s == 1) throw std::runtime_error("循环依赖：" + p.id);
        s = 1;
        for (const auto& dep : p.dependencies) {
            auto it = by_id.find(dep);
            if (it == by_id.end()) throw std::runtime_error("缺少依赖：" + dep);
            visit(*it->second);
        }
        s = 2;
        result.push_back(p);
    };

    for (const auto& p : plugins) visit(p);
    return result;
}
```

`state` 记录三种状态，遇到“访问中”说明绕回来了，也就是循环依赖。报错时列出环路，比随便选一个顺序加载有用得多。

## 9.5 循环依赖是怎么长出来的

拓扑排序能报出环，但报出来的时候已经是发布之后了。值得看看环是怎么一步步长成的。

两个插件。`lint` 提供拼写检查，`docs` 提供文档内容。一开始只有 `lint` 依赖 `docs`，因为检查拼写要先拿到文本。方向单向，排序没问题。

三个月后，`docs` 加了一个功能，保存时顺手查一遍拼写，遇到错误提示用户。实现上只需要在保存钩子里调用 `lint` 的 `spell.check`。代码里只有一行 require，看起来是个小功能。

两个插件单独开发、单独测试，都没问题。CI 里也没人同时装两个。用户两个都装之后，宿主在拓扑排序时报错，两个插件都加载失败，整个编辑器退化成只有一个空窗口。

为什么当时看起来合理。因为两边都只是“顺手查一个东西”，而“顺手”这一层在代码里就一行。环的成本隐藏在这一行后面，单片看代码看不出。

三种拆法，代价不同。

| 拆法 | 适用 | 代价 |
|---|---|---|
| 抽一个底层服务给两边用 | 两边都需要同一份数据 | 宿主多一个契约，长期要维护 |
| 其中一个方向改成事件 | 只需要通知，不需要回答 | 还得写异步和重试，不适用需要即时结果的地方 |
| 两边都改成延迟代理 | 开发期，先把启动跑通 | 问题推到运行期，首帧可能拿不到服务 |

第一种最干净。把“取文档文本”抽成宿主提供的 `core.document`，`lint` 和 `docs` 都依赖它，不再相互依赖。宿主本来就拥有文档，这个服务本来就该在宿主里。

还有一类更阴蔽的环。两个插件的服务名不一样，代码里看不出互相依赖，实际上 A 提供的服务内部又 require 了 B，B 又 require 了 A。拓扑排序只看清单，看不见这种运行期的环。所以报错时要把完整的环路径打出来，不能只说“发现循环依赖”。

## 9.6 卸载顺序

卸载要按加载的相反顺序。后加载的插件可能依赖前面的，先卸载后面的更安全。

```cpp
void unload_all(std::vector<LoadedPlugin>& plugins) {
    for (auto it = plugins.rbegin(); it != plugins.rend(); ++it) {
        if (it->shutdown) it->shutdown();
        registry_.remove_owner(it->id);
        bus_.remove_owner(it->id);
        services_.remove_owner(it->id);
        resources_.release_owner(it->id);
    }
    plugins.clear();
}
```

四行清理对应四种注册。少写一行，就会有东西留在表里，下次发事件或查服务时访问到已经卸载的插件。

这四个 `remove_owner` 可以把它们合并成一个“插件注销”函数，减少遗漏。

```cpp
void unregister_all(const std::string& owner) {
    registry_.remove_owner(owner);
    bus_.remove_owner(owner);
    services_.remove_owner(owner);
    resources_.release_owner(owner);
}
```

以后加了新的注册表，只需要改这一个函数。

## 9.7 热重载的中间态

开发插件时每次改完都要重启宿主，一分钟一轮，一天就磨掉了耐心。热重载能把这个循环缩到两秒，但中间态比“启动”和“卸载”都难写。

热重载不是一个动作，是一串动作。

![图 9-2　热重载先把状态落下，再清账、卸库、重载、恢复](../images/09/fig9-2-reload.png)

```cpp
bool Host::reload(const std::string& id) {
    publish_state_request(id);                 // 1. 让插件把状态写进自己的 Storage
    if (!unload_plugin(id)) return false;      // 2. 撤注册、等在途调用结束
    flush_deferred();
    if (!load_plugin(manifest_of(id))) return false;   // 3. 重新加载
    publish_state_restore(id);                 // 4. 通知它读回状态
    return true;
}
```

四步里每一步都有真实的坑。

**状态丢了。** 插件内存里的文档缓存、连接池、计数器全没了。用户看到的是“重载之后要重新登录”。解决靠插件自己把重要状态写进 `Storage`，宿主只负责在重载前后发两个通知，不替它保存。

**回调变成两份。** 卸载时如果只撤了命令表，忘了撤事件订阅，重载后订阅变成两份。用户一保存，日志写两遍，网络请求发两次。这个 bug 很隐蔽，因为功能“正常”，只是重复。

**画面叠了两层。** 旧图层没撤，像素还在。新插件在自己的图层重新画一遍，两层半透明叠在一起，颜色明显变深。表现是“重载之后颜色不对”，再重载一次更深。

**依赖它的插件崩了。** 重载窗口里 `require` 返回空。依赖方如果没判空，直接解引用。所以重载应该串行化，并且在重载窗口里给依赖方发一条 `service.unavailable` 通知，让它先停掉定时任务。

热重载只适合开发环境。上线后改插件还是走完整的卸载加重装，因为用户的现场里还有没保存的数据，不能为了省一次重启去赌中间态。

## 9.8 主循环

主循环负责读输入、查表、执行。

```cpp
void run_loop() {
    std::string line;
    while (std::getline(std::cin, line)) {
        if (line == "quit") break;
        if (line.empty()) continue;

        auto [name, args] = split_first_space(line);
        const Command* cmd = registry_.find(name);
        if (!cmd) {
            log_info("未知命令：" + name);
            continue;
        }

        current_plugin_ = cmd->owner;
        try {
            cmd->run(args.c_str());
        } catch (const std::exception& e) {
            log_error("命令失败：" + cmd->owner + " " + e.what());
        }
        current_plugin_.clear();
    }
}
```

`current_plugin_` 在命令执行期间设置，日志和事件用它确定归属。执行完清空，避免下一次记录挂错名字。

`try/catch` 包住命令执行，一个插件出错不影响主循环。

## 9.9 插件之间的调用

插件 A 想用插件 B 的服务，完整路径是这样。

```text
A 初始化
  -> api->require_service("example.storage")
     -> 宿主查服务表
        -> 找到 B 注册的实现
           -> 返回代理对象
A 使用
  -> proxy->read("config.json")
     -> 宿主转发到 B
        -> 返回内容
```

对 A 来说只有两步：取服务，调用。中间的转发由宿主完成。

如果 B 崩溃，代理调用会失败。A 要处理这种情况，通常是降级或者提示用户。

跨进程时，代理的调用要带超时，否则 B 卡住会让 A 一起卡住。

## 9.10 一次跨进程调用的失败分支

上一节画的是顺利情况。真实情况里有一半的调用会走到失败分支。

一次跨进程调用在宿主里拆成五步。序列化请求、写管道、等应答、读应答、反序列化。每一步都可能失败，而失败的代价不一样。

**B 进程没起来。** 插件进程启动失败，或者启动到一半崩了。这种失败应该立即返回，不要等超时。等三秒再告诉用户“保存失败”，用户已经点了三次。

**B 崩在调用中途。** 管道读到 EOF。这是确定的崩溃信号，立即判定，同时启动重启流程。重启之后 B 会重新 `plugin_init` 并重注册服务，代理下一次调用应该能重新找到它。如果代理缓存了服务地址，重启之后就是悬空指针。

**B 卡住了。** 一直不回也不断。只能靠超时。超时之后除了返回失败，还要把这个提供方标记为不健康，接下来的调用直接短接，避免每次请求都白等一个超时。

**应答被截断。** 读到一半 EOF，剩下的字节永远不来。没有长度前缀的话，反序列化会把后面别的消息的字节当成自己的字段，结果是一个完全不相关的值，不崩，但数据全错。

```cpp
bool read_frame(int fd, std::string& out) {
    uint32_t n = 0;
    if (!read_exact(fd, &n, sizeof(n))) return false;    // 连接断了
    if (n > 8u * 1024 * 1024) return false;              // 长度离谱，直接断开
    out.resize(n);
    return read_exact(fd, out.data(), n);                // 读不满就是截断
}
```

一次真实的故障是这样。保存按钮点下去卡三秒，但只在装了某个第三方插件的机器上出现。日志里每次保存都有一条超时，没有其他异常。查下去发现那个插件进程在三天前就因为显卡驱动问题崩了，宿主的子进程监控只在启动时检查一次，之后没管。管道已经断了，请求写进去没人读，每次都等到超时。

修复不是把超时调短，而是在管道上挂一个读线程，读到 EOF 就立即判定进程死亡并重启。监控“进程还在不在”靠不住，进程可能变成僵尸；监控“管道还能不能写”更直接。

## 9.11 一个完整的插件接口

把前面所有内容合起来，`PluginApi` 会长到十几个字段。

```cpp
typedef struct PluginApi {
    uint32_t size;
    uint32_t version;

    // 命令与钩子
    void (*register_command)(const PluginCommand* cmd);
    int (*register_hook)(const char* name, HookFn fn);

    // 事件
    void (*on_event)(const char* type, EventFn fn, int kind);

    // 服务
    void* (*require_service)(const char* name);
    int (*provide_service)(const char* name, void* impl);

    // 日志与配置
    void (*log_info)(const char* msg);
    void (*log_error)(const char* msg);

    // 能力查询
    int (*supports)(const char* feature);

    // 扩展点
    int (*contribute)(const char* point, const void* data);

} PluginApi;
```

字段一多，结构体就变得笨重。有两种缓解方式。

**分组。** 把相关的能力放进子结构体，比如 `PluginApi::services` 里放服务相关的函数。

```cpp
typedef struct ServiceApi {
    void* (*require)(const char* name);
    int (*provide)(const char* name, void* impl);
} ServiceApi;

typedef struct PluginApi {
    uint32_t size;
    uint32_t version;
    ServiceApi services;
    // ...
} PluginApi;
```

**按需获取。** 主接口只保留最基础的部分，其他能力通过 `query_interface` 获取。

```cpp
typedef struct PluginApi {
    uint32_t size;
    uint32_t version;
    void* (*query_interface)(const char* name);
} PluginApi;
```

插件需要渲染能力时，`query_interface("render")` 拿到一个 `RenderApi*`。不需要的能力完全不加载。

第二种更适合大系统，因为接口可以按模块独立演进。

## 9.12 配置与状态

插件需要保存自己的配置和状态。

宿主给每个插件一个隔离的目录，按插件编号分配。

```text
data/
  plugins/
    com.example.hello/
      config.json
      cache/
      logs/
```

插件拿到的是一个能力对象，不是真实路径。

```cpp
class Storage {
public:
    std::string read(const std::string& key);
    void write(const std::string& key, const std::string& value);
};
```

不同插件拿到不同的 `Storage` 实例，根目录不同。插件不知道自己的真实路径，也就无法访问别人的目录。

## 9.13 装配完成后的五项验证

结构装好之后，不能只看“能启动”。下面五项每项对应一类真实事故。

**故意让一个插件初始化失败。** 在它的 `plugin_init` 里返回非零，或者直接断点。其他插件应该照常加载，命令都能用，日志里有一条明确的失败记录。如果整个应用起不来，说明第 5 步没有容错。

**启动后立刻退出。** 正常关闭，然后检查四张表为空。不为空说明有东西没撤干净，下次启动时可能重名冲突。

**杀掉一个第三方插件进程。** 应用不应该退出，界面上那个插件的功能变成不可用，最好能自动重启。如果整个窗口黑掉，说明进程监控和降级都没做。

**热重载一个被依赖的插件。** 重载完成后功能正常，日志不重复，画面不叠层。任何一项不对，就是撤注册或者图层清理有漏。

**造一个依赖环。** 两个插件互相依赖，宿主应该报出环路径并跳过这两个，其他插件正常。如果直接卡住或者崩掉，说明排序里没有环路检测。

五项都过，才算是把结构装上了。后面出问题，排查也能顺着这五条找到位置。

## 9.14 这个结构解决了什么

回头看第 1 章列的五种失控。

**命名冲突。** 命令用 `owner` 标记归属，扩展点用命名空间，服务用 `core.*` 保留前缀。

**故障扩散。** 命令执行包 `try/catch`，事件按订阅者类型决定异常处理，第三方插件独立进程。

**协作缺失。** 服务注册表让插件之间可以互相调用，不必通过事件喊话。

**版本断裂。** `size` 加版本号加能力协商，三层保证旧插件继续工作。

**顺序混乱。** 优先级、显式依赖、拓扑排序，三种来源共同决定。

五种都有对应的结构。但结构不是免费的，下一章算账。
