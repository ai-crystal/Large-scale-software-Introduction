# 第 9 章 把结构装回去

## 9.1 前八章留下的零件

把前八章的决定列出来。

**内核。** 保留生命周期、服务注册、事件分发、资源与权限。不包含任何业务逻辑。

**扩展点。** 三种形态（列表、管道、单点），声明式和命令式两种提交方式，统一的标识规范。

**契约。** `size` 保证结构兼容，版本号保证语义兼容，能力协商处理细粒度特性。

**事件与钩子。** 订阅者分观察者、修改者、拦截者三类，顺序由优先级和显式依赖共同决定，短路要记日志。

**进程模型。** 按信任级别分组，内置插件同进程，第三方插件独立进程。

**服务注册表。** 命名空间隔离，支持必需依赖和可选依赖，跨进程用代理。

**渲染服务。** 句柄管理资源，命令缓冲提交绘制，图层隔离插件。

这些零件分开看都清楚，装在一起会有新的问题。这一章处理装的过程。

## 9.2 启动顺序

启动顺序决定了哪些东西必须比哪些东西早存在。

```text
1. 创建内核对象（注册表、总线、服务表、资源管理器）
2. 加载宿主自己的内置命令和内置服务
3. 扫描插件目录，读取清单
4. 按依赖关系排序
5. 逐个加载插件，调用 plugin_init
6. 事件总线开始接受事件
7. 进入主循环
```

几个容易出错的地方。

**第 2 步不能省。** 宿主自己的命令要在插件之前注册，否则插件注册的命令名可能和宿主冲突，宿主反而被拒绝。

**第 5 步要容错。** 一个插件初始化失败，跳过它，继续下一个。失败的插件留下的注册要清理干净。

**第 6 步有边界。** 插件加载过程中可能已经发了事件，但此时总线还不完整。稳妥的做法是加载阶段把事件缓存，加载完再统一分发。

## 9.3 依赖排序

插件之间有依赖时，加载顺序不能随意。

拓扑排序的写法。

```cpp
std::vector<Manifest> sort_by_dependency(const std::vector<Manifest>& plugins) {
    std::map<std::string, const Manifest*> by_id;
    for (const auto& p : plugins) by_id[p.id] = &p;

    std::vector<Manifest> result;
    std::map<std::string, int> state;   // 0 未访问，1 访问中，2 完成

    std::function<void(const Manifest&)> visit = [&](const Manifest& p) {
        int& s = state[p.id];
        if (s == 2) return;
        if (s == 1) throw std::runtime_error("循环依赖：" + p.id);
        s = 1;
        for (const auto& dep : p.dependencies) {
            auto it = by_id.find(dep);
            if (it == by_id.end()) throw std::runtime_error("缺少依赖：" + dep);
            visit(*it->second);
        }
        s = 2;
        result.push_back(p);
    };

    for (const auto& p : plugins) visit(p);
    return result;
}
```

`state` 记录三种状态，遇到“访问中”说明绕回来了，也就是循环依赖。报错时列出环路，比随便选一个顺序加载有用得多。

## 9.4 卸载顺序

卸载要按加载的相反顺序。后加载的插件可能依赖前面的，先卸载后面的更安全。

```cpp
void unload_all(std::vector<LoadedPlugin>& plugins) {
    for (auto it = plugins.rbegin(); it != plugins.rend(); ++it) {
        if (it->shutdown) it->shutdown();
        registry_.remove_owner(it->id);
        bus_.remove_owner(it->id);
        services_.remove_owner(it->id);
        resources_.release_owner(it->id);
    }
    plugins.clear();
}
```

四行清理对应四种注册。少写一行，就会有东西留在表里，下次发事件或查服务时访问到已经卸载的插件。

这四个 `remove_owner` 可以把它们合并成一个“插件注销”函数，减少遗漏。

```cpp
void unregister_all(const std::string& owner) {
    registry_.remove_owner(owner);
    bus_.remove_owner(owner);
    services_.remove_owner(owner);
    resources_.release_owner(owner);
}
```

以后加了新的注册表，只需要改这一个函数。

## 9.5 主循环

主循环负责读输入、查表、执行。

```cpp
void run_loop() {
    std::string line;
    while (std::getline(std::cin, line)) {
        if (line == "quit") break;
        if (line.empty()) continue;

        auto [name, args] = split_first_space(line);
        const Command* cmd = registry_.find(name);
        if (!cmd) {
            log_info("未知命令：" + name);
            continue;
        }

        current_plugin_ = cmd->owner;
        try {
            cmd->run(args.c_str());
        } catch (const std::exception& e) {
            log_error("命令失败：" + cmd->owner + " " + e.what());
        }
        current_plugin_.clear();
    }
}
```

`current_plugin_` 在命令执行期间设置，日志和事件用它确定归属。执行完清空，避免下一次记录挂错名字。

`try/catch` 包住命令执行，一个插件出错不影响主循环。

## 9.6 插件之间的调用

插件 A 想用插件 B 的服务，完整路径是这样。

```text
A 初始化
  -> api->require_service("example.storage")
     -> 宿主查服务表
        -> 找到 B 注册的实现
           -> 返回代理对象
A 使用
  -> proxy->read("config.json")
     -> 宿主转发到 B
        -> 返回内容
```

对 A 来说只有两步：取服务，调用。中间的转发由宿主完成。

如果 B 崩溃，代理调用会失败。A 要处理这种情况，通常是降级或者提示用户。

跨进程时，代理的调用要带超时，否则 B 卡住会让 A 一起卡住。

## 9.7 一个完整的插件接口

把前面所有内容合起来，`PluginApi` 会长到十几个字段。

```cpp
typedef struct PluginApi {
    uint32_t size;
    uint32_t version;

    // 命令与钩子
    void (*register_command)(const PluginCommand* cmd);
    int (*register_hook)(const char* name, HookFn fn);

    // 事件
    void (*on_event)(const char* type, EventFn fn, int kind);

    // 服务
    void* (*require_service)(const char* name);
    int (*provide_service)(const char* name, void* impl);

    // 日志与配置
    void (*log_info)(const char* msg);
    void (*log_error)(const char* msg);

    // 能力查询
    int (*supports)(const char* feature);

    // 扩展点
    int (*contribute)(const char* point, const void* data);

} PluginApi;
```

字段一多，结构体就变得笨重。有两种缓解方式。

**分组。** 把相关的能力放进子结构体，比如 `PluginApi::services` 里放服务相关的函数。

```cpp
typedef struct ServiceApi {
    void* (*require)(const char* name);
    int (*provide)(const char* name, void* impl);
} ServiceApi;

typedef struct PluginApi {
    uint32_t size;
    uint32_t version;
    ServiceApi services;
    // ...
} PluginApi;
```

**按需获取。** 主接口只保留最基础的部分，其他能力通过 `query_interface` 获取。

```cpp
typedef struct PluginApi {
    uint32_t size;
    uint32_t version;
    void* (*query_interface)(const char* name);
} PluginApi;
```

插件需要渲染能力时，`query_interface("render")` 拿到一个 `RenderApi*`。不需要的能力完全不加载。

第二种更适合大系统，因为接口可以按模块独立演进。

## 9.8 配置与状态

插件需要保存自己的配置和状态。

宿主给每个插件一个隔离的目录，按插件编号分配。

```text
data/
  plugins/
    com.example.hello/
      config.json
      cache/
      logs/
```

插件拿到的是一个能力对象，不是真实路径。

```cpp
class Storage {
public:
    std::string read(const std::string& key);
    void write(const std::string& key, const std::string& value);
};
```

不同插件拿到不同的 `Storage` 实例，根目录不同。插件不知道自己的真实路径，也就无法访问别人的目录。

## 9.9 这个结构解决了什么

回头看第 1 章列的五种失控。

**命名冲突。** 命令用 `owner` 标记归属，扩展点用命名空间，服务用 `core.*` 保留前缀。

**故障扩散。** 命令执行包 `try/catch`，事件按订阅者类型决定异常处理，第三方插件独立进程。

**协作缺失。** 服务注册表让插件之间可以互相调用，不必通过事件喊话。

**版本断裂。** `size` 加版本号加能力协商，三层保证旧插件继续工作。

**顺序混乱。** 优先级、显式依赖、拓扑排序，三种来源共同决定。

五种都有对应的结构。但结构不是免费的，下一章算账。
