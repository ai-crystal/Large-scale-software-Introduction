# 附录

## 附录 A 二十三种模式速查

每一行给出四样东西：它要解决的那个反复出现的问题、核心角色、一句话判断、最容易犯的错。

### 创建型

<div class="ref-table" markdown="1">

| 模式 | 解决的问题 | 核心角色 | 一句话判断 | 常见误用 |
|---|---|---|---|---|
| 单例 | 某个资源全局只能有一份，且创建代价高 | 私有构造、静态访问点 | 这份东西真的只能有一份吗 | 把全局变量包装成单例 |
| 工厂方法 | 创建哪个具体类要由子类或配置决定 | 产品接口、创建者、具体产品 | 调用方还会不会再加新的产品类型 | 一个工厂里塞十种产品 |
| 抽象工厂 | 一整套相关产品必须整体替换 | 抽象工厂、具体工厂、产品族 | 这些产品之间有没有配套关系 | 产品族只有一个，硬拆成族 |
| 建造者 | 对象参数很多，装配分很多步 | 建造者、指挥者、产品 | 构造参数是否超过四五个 | 把简单赋值也做成建造者 |
| 原型 | 新对象是已有对象的微调 | 原型接口、克隆方法 | 是不是“复制一份再改两处” | 浅拷贝导致共享内部状态 |

</div>

### 结构型

<div class="ref-table" markdown="1">

| 模式 | 解决的问题 | 核心角色 | 一句话判断 | 常见误用 |
|---|---|---|---|---|
| 适配器 | 两套不兼容的接口要对接 | 目标接口、适配器、被适配者 | 是不是第三方接口改不了 | 借适配器掩盖设计错误 |
| 桥接 | 两个维度各自独立变化 | 抽象、实现者、细化抽象 | 是不是有两组正交的变化 | 只有一个维度就拆成桥 |
| 组合 | 单个对象和整体要一视同仁 | 组件接口、叶子、容器 | 数据结构是不是树 | 用组合做深层嵌套的配置 |
| 装饰器 | 动态叠加能力，不想改原类 | 组件、装饰器、具体组件 | 能力是否需要任意组合 | 装饰层数失控，读不出实际行为 |
| 外观 | 一组子系统调用太繁琐 | 外观、子系统 | 调用方是否只想要一个入口 | 把业务逻辑塞进外观 |
| 享元 | 大量对象里大部分状态可共享 | 享元工厂、享元、外部状态 | 重复对象是否占了大头内存 | 把可变状态也共享了 |
| 代理 | 访问真实对象前要加一层控制 | 主题接口、代理、真实主题 | 是否需要延迟、权限、缓存、远程 | 代理里塞业务逻辑 |

</div>

### 行为型

<div class="ref-table" markdown="1">

| 模式 | 解决的问题 | 核心角色 | 一句话判断 | 常见误用 |
|---|---|---|---|---|
| 责任链 | 一个请求可能由多个对象之一处理 | 处理者接口、具体处理者 | 处理者会不会增加、顺序会不会变 | 链条过长，不知道谁处理了 |
| 命令 | 操作需要排队、记录、撤销 | 命令接口、具体命令、接收者、调用者 | 是否要把“操作”当成数据 | 命令自己做业务，不交给接收者 |
| 解释器 | 用户要在运行时写出可求值的规则 | 表达式、终结符、非终结符、上下文 | 规则语法是否会持续扩展 | 语法一大还手写解释器 |
| 迭代器 | 遍历方式要独立于内部结构 | 迭代器、聚合 | 是否有多于一种走法 | 遍历中修改集合 |
| 中介者 | 多个对象互相通信，关系成网 | 中介者、同事 | 通信关系是否已经形成网 | 中介者变成上帝对象 |
| 备忘录 | 要回到之前某个时刻的状态 | 原发器、备忘录、管理者 | 状态能否用较小代价保存 | 浅拷贝、快照对外暴露 |
| 观察者 | 变化要通知多个不固定的对象 | 主题、观察者 | 下游数量和种类是否会增加 | 忘记退订、通知风暴 |
| 状态 | 同一操作在不同状态下行为不同 | 上下文、状态接口、具体状态 | 状态之间是否有转移路径 | 用状态模式实现一个布尔开关 |
| 策略 | 同一件事有几套可替换的算法 | 上下文、策略、具体策略 | 算法是否会被替换或新增 | 选择逻辑又变成大 if |
| 模板方法 | 多套流程共享骨架，只有几步不同 | 抽象类、模板方法、钩子 | 变化的是步骤，不是流程 | 继承层级失控 |
| 访问者 | 元素类型稳定，操作不断增加 | 访问者、元素、对象结构 | 加操作多还是加类型多 | 元素类型频繁新增 |

</div>

## 附录 B 容易混淆的七组模式

模式之间最难的从来不是“怎么实现”，而是“现在该用哪个”。下面七组最常被问。

### 策略 / 状态

结构几乎一样，语义相反。策略是换算法，由外部决定用哪个，策略之间彼此独立；状态是换阶段，由内部或者规则表决定转到哪，状态之间有路径。

判断方法：如果“当前是哪个”决定了“下一步能做什么”，是状态；如果只是“用哪套算法算”，是策略。

### 命令 / 备忘录

两者都能撤销。命令记“做了什么”，靠反向执行回退；备忘录记“是什么状态”，靠整体恢复回退。

命令省内存但要求每个操作可逆，备忘录一定正确但占空间。日常编辑用命令，复杂操作用备忘录做快照。

### 观察者 / 中介者

观察者是广播，主题不知道有谁在听；中介者是定向转发，中间人认识每一个同事，可以拦截、改写、合并。

观察者解“一对多通知”，中介者解“多对多通信”。

### 适配器 / 装饰器 / 代理

三个都是“包一层”，意图完全不同。

适配器改接口，让不兼容的东西能对接；装饰器加能力，接口不变；代理控访问，接口不变但在前面加一道控制。

判断方法：调用方看到的接口变没变。变了是适配器，没变是装饰器或者代理；再问“这层是为了加功能还是为了加控制”，加功能是装饰器，加控制是代理。

### 外观 / 中介者

外观是单向的，调用方走外观到子系统，子系统不认识外观；中介者是双向的，同事主动通知中介者。

外观简化调用，中介者集中通信。

### 工厂方法 / 模板方法

工厂方法常常是模板方法里的一步：父类的流程里有一句“创建对象”，创建哪个由子类决定。

区别在意图。工厂方法回答“创建哪个类”，模板方法回答“流程怎么走”。

### 组合 / 迭代器 / 访问者

三者经常一起出现在树的处理里。

组合负责把树搭起来，迭代器负责把树走一遍，访问者负责走到每个节点时做什么。它们不是竞争关系，而是同一件事的三个阶段。

## 附录 C 从问题出发的选择路径

不要从“我要用哪个模式”出发，要从“我现在卡在哪”出发。先判断麻烦出在创建、组合，还是协作，再到对应的小节里找最接近的那一行。

### 卡在创建

| 你遇到的情况 | 可以看 |
|---|---|
| 创建哪一个类，要到运行的时候才知道 | 工厂方法 |
| 一整套相关对象必须配套替换 | 抽象工厂 |
| 参数太多，装配要分好几步 | 建造者 |
| 新对象只是已有对象改两处 | 原型 |
| 某个资源全局只能有一份 | 单例（先确认真的只能有一份） |

### 卡在组合

| 你遇到的情况 | 可以看 |
|---|---|
| 接口不兼容，而对方是第三方，改不了 | 适配器 |
| 两个维度各自独立变化，继承已经数不清 | 桥接 |
| 单个对象和整体需要一视同仁 | 组合 |
| 能力要能任意叠加，又不想改原类 | 装饰器 |
| 一组子系统的调用太繁琐 | 外观 |
| 大量对象里大部分状态重复 | 享元 |
| 访问真实对象之前要加一层控制 | 代理 |

### 卡在协作

| 你遇到的情况 | 可以看 |
|---|---|
| 一个请求可能由多个对象之一处理 | 责任链 |
| 操作要排队、记录、撤销 | 命令 |
| 用户要在运行时写出可求值的规则 | 解释器 |
| 遍历方式要能换，又不能暴露内部结构 | 迭代器 |
| 多个对象互相通信，关系已经成网 | 中介者 |
| 要回到之前某个时刻的状态 | 备忘录 |
| 一个变化要通知数量不固定的下游 | 观察者 |
| 同一操作在不同状态下行为不同 | 状态 |
| 同一件事有几套可替换的算法 | 策略 |
| 流程固定，只有少数几步不同 | 模板方法 |
| 元素类型稳定，操作不断增加 | 访问者 |

这几张表只能缩小范围，不能替你决定。真正的判断还要回答三个问题：这个变化过去发生过吗，将来还会发生吗，加这一层之后谁来承担理解成本。

## 附录 D 十条误用清单

以下十条，是模式被用坏时最常见的形态。

**一、为了用模式而用模式。** 代码里出现一个接口、一个实现类，然后就没了。这一层没有带来任何替换能力，只带来了跳转。

**二、在不会变化的地方加抽象。** 抽象是给变化留的位置。没有变化，位置就是空的。

**三、把简单逻辑拆成五个类。** 一个判断加一个赋值，拆成策略加工厂，读代码的人要在五个文件之间跳。简单逻辑就直接写。

**四、用模式掩盖设计错误。** 接口不兼容，本该重新设计；硬套一个适配器，错误被包住了，问题还在。

**五、全局单例泛滥。** 单例最大的诱惑是“到处都能拿到”。一旦泛滥，依赖关系就从代码里消失了，测试也没法替换。

**六、观察者不退订。** 页面关了、插件卸了，订阅还在。内存泄漏往往就是这么来的。

**七、中介者变成上帝对象。** 所有联动规则堆在一个类里，改一处要想清楚影响十几处。这时候该做的是把业务规则下沉，不是继续加分支。

**八、继承层级超过三层。** 模板方法加模板方法，再加一层子类，调试要跳四层。超过三层就该考虑组合。

**九、装饰层数失控。** 一个对象被包了七层，出问题时不知道哪一层改了什么。装饰要能打印出当前链条。

**十、把模式的类名当文档。** `XxxManager`、`XxxHelper`、`XxxProcessor` 堆在一起，模式名字有了，职责反而更模糊。名字应该说明职责，不是说明用了哪个模式。

## 附录 E 收尾

二十三章讲完，回到前言里那句话：模式是工具，不是目标。

这本书里每一个模式，都是从一段真实的麻烦开始的：一个函数越来越长，一个分支越来越多，一次改动牵动一片。模式给出的解法，本质都是同一件事——**把变化的地方找出来，给它一个明确的边界，让将来改它的时候不用动别的地方**。

所以判断要不要用某个模式，最终都可以归结成两个问题。

**第一，这里的变化真的发生过吗？** 过去半年改过几次？每次改动是不是都要碰同一批文件？如果是，这个位置值得一个边界。如果只是“将来可能会变”，先别急。

**第二，加上这个边界之后，理解成本落在谁身上？** 很多时候，写的人省事了，读的人要多跳三层。如果读的人比写的人多，这笔账就要重新算。

模式的价值不在于记住二十三个名字，而在于遇到麻烦时能想起来：这类问题有人整理过解法，我应该去看一眼，而不是从头再发明一次。

至于用不用，什么时候用，用到什么程度，那是你的判断。书能做的，只是把名字和边界讲清楚。
