# 第 9 章 装饰器：一层层加上能力

## 9.1 一个 HTTP 客户端

系统里有一个 HTTP 客户端，负责调外部接口。

最初它只有“发请求、拿响应”两个功能。后来需求一个个来。

**要记日志。** 每次请求的方法、地址、耗时、状态码都要记下来。

**要重试。** 网络抖动时自动重试三次，间隔递增。

**要缓存。** 某些 GET 请求五分钟内不重复发。

**要鉴权。** 请求头里自动加上令牌，令牌过期时刷新一次。

最直接的实现是全部塞进客户端里。

```text
class HttpClient
  send(req)
    log("start", req)
    if cache.has(req): return cache.get(req)
    for i in 1..3:
        try
            resp = do_send(with_token(req))
            cache.put(req, resp)
            log("ok", resp)
            return resp
        catch e:
            if i == 3: throw
            sleep(backoff(i))
```

这段代码能跑，但有三个问题。

**每个功能都不可拆。** 某个调用方不需要缓存，也没法关掉。某个内部接口不需要鉴权，也得走一遍。

**加功能就改这个函数。** 下次要加“请求体压缩”，又得往这个函数里插一段。

**顺序固定。** 日志在缓存之前，重试在外层。如果某个场景需要“先鉴权再记日志”，改不了。

## 9.2 用包装代替修改

装饰器模式的思路是：每个功能做成一个包装层，包装层和原对象实现同一个接口，层层套起来。

它包含四个角色。

**组件接口。** 描述客户端能做什么，比如“发送请求”。

**具体组件。** 真正干活的实现，只负责发请求。

**装饰器基类。** 实现组件接口，内部持有一个组件引用，默认把调用原样转发。

**具体装饰器。** 继承装饰器基类，在转发前后加上自己的行为。

用结构描述。

```text
interface HttpClient
  send(req) : Response

class BasicClient implements HttpClient
  send(req) { return do_send(req) }

class LoggingClient implements HttpClient
  inner : HttpClient
  send(req)
    log("start", req)
    resp = inner.send(req)
    log("end", resp.status)
    return resp

class RetryClient implements HttpClient
  inner : HttpClient
  send(req)
    for i in 1..3:
        try: return inner.send(req)
        catch e: if i == 3 throw; sleep(backoff(i))

class AuthClient implements HttpClient
  inner : HttpClient
  send(req) { return inner.send(with_token(req)) }
```

## 9.3 协作过程

装配时按需要套。

```text
client = new LoggingClient(
             new RetryClient(
                 new AuthClient(
                     new BasicClient())))
```

调用 `client.send(req)` 时，调用沿包装层向内传递，再沿原路返回。

```text
Logging 开始记录
  Retry 第一次尝试
    Auth 加上令牌
      Basic 真正发送
    Auth 返回
  Retry 判断成功
Logging 记录结果
```

每一层只关心自己那件事。日志层不管重试，重试层不管鉴权，鉴权层不管怎么发。

如果某个调用方不需要缓存，就不套缓存层。如果要调整顺序，就换个套法。原对象一行都不用改。

## 9.4 装饰器的顺序

顺序会直接影响结果。

**日志在外、重试在内。** 记一次请求，包含所有重试。日志里看到的是“一次调用，耗时三秒”。

**重试在外、日志在内。** 每次重试都记一条。日志里看到的是“三次调用，每次一秒”。

两种都有用，取决于你想看什么。前者适合统计接口整体耗时，后者适合排查每次尝试的失败原因。

**鉴权在重试内、重试在外。** 每次重试都会重新检查令牌。如果令牌在重试期间过期，第二次会自动刷新。

**鉴权在重试外。** 只在最开始检查一次。重试期间令牌过期，后面几次都会失败。

顺序不是随便排的，要按业务语义确定。装配的地方应该写注释，说明为什么这么排。

## 9.5 顺序之外的三个坑

顺序排对了，还有三个坑跟顺序无关，却决定这层装饰器能不能用。

**重试要求请求可以重复发。** 重试层意味着同一个请求可能被发两次、三次。如果请求是扣款或下单，重发就是重复扣款。重试层自己判断不了业务是否幂等，它只能在请求结构上要一个幂等键，让服务端按键去重。

```cpp
struct Request {
    std::string method;
    std::string url;
    std::string body;
    std::string idempotency_key;  // 业务方生成，重试期间保持不变
    int timeout_ms = 3000;
};
```

重试层在循环里只改超时和退避，不动这个键。退避要加几十毫秒量级的随机抖动，多个客户端同时失败又同时重试，会把刚缓过来的服务再打垮一次。缺了幂等键，重试层本身就是风险，不是保障。

**缓存键要包含所有影响结果的输入。** 缓存层按请求算键。最省事的写法是把整个请求序列化后哈希，可请求里带着鉴权令牌，令牌每次刷新都不同，缓存永远不命中；把令牌从键里去掉，又会让甲用户的响应被乙用户读到。

```cpp
std::string cache_key(const Request& req) {
    return req.method + " " + req.url + " " + req.body +
           " user=" + req.user_id;   // 用身份，不用令牌
}
```

判断方法很简单，问一句，两个请求在这几个字段相同时，服务端返回的东西一定一样吗。答不上来，就说明还有字段漏在键外面。语言、时区、客户端版本这类字段最容易被漏掉。

第三个坑最隐蔽。装饰器对象本身不该持有跨请求的状态。日志层若用一个成员变量累加耗时，两个线程同时进来就会互相覆盖，记出来的数一个偏大一个偏小。每次调用的中间量都放局部变量，装饰器才能被多个调用方共用。

## 9.6 用 C++ 写一层装饰器

接口和包装层都只有十几行，真正要留意的是所有权，以及装配集中在哪。

```cpp
class HttpClient {
public:
    virtual ~HttpClient() = default;
    virtual Response send(const Request& req) = 0;
};

class BasicClient : public HttpClient {
public:
    explicit BasicClient(Endpoint ep) : ep_(std::move(ep)) {}
    Response send(const Request& req) override { return transport_.post(ep_, req); }
private:
    Endpoint ep_;
    Transport transport_;
};

class Decorator : public HttpClient {
public:
    explicit Decorator(std::shared_ptr<HttpClient> inner) : inner_(std::move(inner)) {}
protected:
    std::shared_ptr<HttpClient> inner_;
};

class RetryClient : public Decorator {
public:
    using Decorator::Decorator;
    Response send(const Request& req) override {
        for (int attempt = 1; ; ++attempt) {
            try {
                return inner_->send(req);
            } catch (const TransportError& e) {
                if (attempt >= 3 || !e.retriable()) throw;
                std::this_thread::sleep_for(backoff(attempt));
            }
        }
    }
};
```

`Decorator` 基类把“转发”这件事写了一次，具体装饰器只写自己那一段，样板代码全省。日志层同理，转发前取一个 `steady_clock` 时间戳，转发后算差值打一行，不需要碰接口。持有 `shared_ptr` 而不是裸指针，链上任何一环被别处共享，也不会提前析构。

装配集中在一个函数里，全系统只有这里知道链长什么样。

```cpp
std::shared_ptr<HttpClient> make_client(const Config& cfg) {
    std::shared_ptr<HttpClient> c = std::make_shared<BasicClient>(cfg.endpoint);
    c = std::make_shared<AuthClient>(c);     // 令牌在内，重试时每次重新检查
    c = std::make_shared<RetryClient>(c);    // 重试包住鉴权
    if (cfg.enable_cache) c = std::make_shared<CacheClient>(c);
    c = std::make_shared<LoggingClient>(c);  // 日志最外，记录整体耗时
    return c;
}
```

配置驱动的版本把每层换成一个工厂函数，按名字从表里查，装配函数退化成一次循环。链的顺序由配置给出，那五行注释仍然要留，它是这个顺序唯一的说明。

## 9.7 一个被套坏的客户端

某订单服务给内部接口套了五层，缓存、日志、重试、鉴权、限流。上线一周后出现怪事，运营改了价格，页面半小时后才变。

排查发现缓存层建在重试层外面。第一反应是重试把脏数据带进了缓存，其实不是。重试层对外的语义是“成功就返回，失败就抛异常”，缓存层却只认“返回了响应”这一件事。那次故障期间下游返回 503，503 是一个正常的 `Response` 对象，不是异常，于是被原样存进缓存，TTL 五分钟。后面所有请求命中的都是这条 503。

收拾分三步。

第一步，缓存层自己判断该不该存，只缓存 200 且响应头允许缓存的响应，其余直接透传。这条规则写在缓存层内部，不指望装配处记得。

第二步，写操作之后按资源前缀失效，不按完整 URL 失效。价格变更接口改完立刻清 `/api/product/*`，比等 TTL 到点更可靠。

第三步，给装配顺序补一个测试。用假传输层依次注入超时、503、200，断言日志条数、重试次数、缓存命中这三组数字。谁调错顺序，测试立刻红。

装配之前，把这几条过一遍。

| 检查项 | 不通过会怎样 |
|---|---|
| 被重试的请求带幂等键 | 重复扣款、重复下单 |
| 缓存键覆盖用户、语言、客户端版本 | 串号、看到别人的或过期的数据 |
| 装饰器没有跨请求的成员状态 | 并发下统计与日志互相污染 |
| 每层失败时抛的异常类型一致 | 外层 catch 不到，重试形同虚设 |
| 顺序只在一处定义并配有测试 | 后人调序，问题上线才暴露 |

## 9.8 装饰器与继承

不用装饰器，用继承也能加功能。比如 `LoggingClient extends BasicClient`。

继承的问题是组合爆炸。四个功能，两两组合就是十几种情况。每个组合都要一个子类。

```text
LoggingRetryAuthClient
LoggingAuthClient
RetryAuthClient
...
```

而且继承是编译时确定的，运行时换不了。装饰器是运行时套的，装配逻辑可以根据配置决定套几层。

这就是装饰器最核心的优势：**用组合代替继承，把“加什么功能”从编译时挪到运行时。**

顺带说一句，继承也不是全无位置。一个装饰器如果只是给已有的某层加个固定的小动作，写一个 `final` 的特化类，配合静态装配，能省掉虚调用。但它只能覆盖一种组合，别指望用它当通用方案。

## 9.9 什么时候不该用

**层数太多。** 套了七八层之后，一次调用要在脑子里走一遍俄罗斯套娃。日志里全是各层的记录，反而看不清主流程。

**功能之间强依赖。** 如果缓存层必须知道重试层的内部状态，那它们不该拆成两层，应该合成一个。

**性能敏感。** 每层都是一次虚调用，加上可能的额外开销。每秒几万次调用的热路径，装饰器可能成为瓶颈。

**只有一个固定组合。** 如果所有调用方都需要同样的四层，而且顺序永远不变，那直接写一个组合好的类更简单，不必在装配处套四层。

还有一个更隐蔽的代价，调试。异常从最内层抛出来，栈里连着四层 `send`，每层都长一个样。给每层的异常加上“来自哪一层”的标记，或者干脆只保留最内层的原始栈，读日志的人会轻松很多。

## 9.10 与代理的区别

装饰器和代理的结构几乎一样：都是实现同一个接口，内部持有一个真实对象。

区别在目的和数量。

**装饰器**是为了增强，可以有任意多层，每层加一种能力。调用方通常知道自己套了什么。

**代理**是为了控制访问，通常只有一层。调用方往往不知道自己在跟代理打交道，代理决定了要不要转发、什么时候转发、转发给谁。

一个具体的区别：装饰器会把调用转发给真实对象，几乎总是转发；代理可能不转发，比如权限不足时直接拒绝，或者图片还没加载时先返回占位图。

数量上的差别也会带来设计上的差别。装饰器层数由需求决定，今天是三层，明天可能五层，接口必须假设“上面还有一层”。代理通常只有一层，它的接口可以更贴近真实对象的语义，不必考虑被别人再包一次。

## 9.11 与责任链的区别

两者都是“一层层传递”，但处理方式不同。

**责任链**里，请求通常只被一个处理者处理，处理完就停止。链的作用是“找到能处理的人”。

**装饰器**里，每一层都会执行，而且都会把请求继续往下传。链的作用是“每层都做一点事”。

一个记忆方法：责任链是“传球，投中就停”；装饰器是“过安检，每道都要过”。

从代码上看还有一处差别。责任链的每一环都可能返回一个和输入无关的结果，比如“驳回”；装饰器的返回值一般由最内层决定，外层只能修改或者包装它，不能凭空造一个。

## 9.12 一个判断标准

要不要用装饰器，看三点。

第一，有没有一组可以自由组合的附加功能？有，装饰器合适。

第二，这些功能是不是需要在不修改原对象的前提下加上去？是，装饰器比继承灵活。

第三，组合方式是不是在运行时才能确定？是，装饰器几乎是唯一选择。

如果功能只有一两个固定组合，或者功能之间有强依赖，用继承或者直接写在一起更简单。
