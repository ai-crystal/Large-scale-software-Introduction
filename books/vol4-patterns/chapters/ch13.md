# 第 13 章 责任链：沿着一条链找处理者

## 13.1 报销审批

公司要做一个报销审批功能。

规则是这样的。金额小于五百，组长审批。五百到五千，部门经理审批。五千到五万，总监审批。超过五万，要走总裁办。

最初的实现是一个函数。

```text
approve(amount):
    if amount < 500:
        return leader.approve(amount)
    else if amount < 5000:
        return manager.approve(amount)
    else if amount < 50000:
        return director.approve(amount)
    else:
        return board.approve(amount)
```

这段代码清楚，但改起来麻烦。

**规则会变。** 公司调整审批额度，要改这个函数。加一个“财务复核”环节，也要改。

**审批人可能缺席。** 经理出差时，应该由代理经理审批。这个逻辑往哪放？塞进 `if` 里，函数会越来越长。

**不同业务线的规则不同。** 销售部的额度比研发部高。如果每个业务线都写一个函数，会有大量重复。

## 13.2 把审批人串成一条链

责任链模式的思路是：每个审批人都是一个处理者，处理者知道自己下一个是谁。请求从链头开始，能处理就处理，不能处理就交给下一个。

它包含三个角色。

**处理者接口。** 声明“处理请求”的方法，以及“设置下一个处理者”的方法。

**具体处理者。** 实现处理逻辑。能处理就返回结果；不能处理就看有没有下一个，有就转发。

**客户端。** 构造链，把请求交给链头。

用结构描述。

```text
interface Approver
  set_next(next) : Approver
  approve(req) : Result

class Leader implements Approver
  next : Approver
  approve(req)
    if req.amount < 500: return Result.approved("组长")
    if next == null: return Result.rejected("无人处理")
    return next.approve(req)

class Manager implements Approver
  approve(req)
    if req.amount < 5000: return Result.approved("经理")
    if next == null: return Result.rejected("无人处理")
    return next.approve(req)
```

## 13.3 协作过程

1. 启动时按规则构造链：组长 → 经理 → 总监 → 总裁办。
2. 客户端把请求交给组长。
3. 组长判断金额，符合自己的额度就批准，返回。
4. 不符合，调用 `next.approve`，请求传给经理。
5. 一直传到能处理的那一环。
6. 如果传到最后都没人处理，返回“无人处理”。

整个过程中，客户端只认识链头，不知道链有多长、每一环是谁。

加一个“财务复核”环节，只需要在构造链时插进去，处理者类不用改。调整额度，只改对应处理者的判断条件。

## 13.4 纯链与不纯链

责任链有两种形态。

**纯链。** 一个请求必须被某一环处理，处理完就停止。如果没人处理，视为失败。审批流是典型的纯链。

**不纯链。** 每一环都可以处理一部分，处理完继续往下传。日志链、过滤器链是典型的不纯链。

不纯链更像装饰器，区别在于：责任链的每一环可以选择“不处理”，装饰器的每一层通常会执行。

写代码时要明确是哪一种。纯链要有“无人处理”的兜底，不纯链要定义“某一环失败后是中断还是继续”。

## 13.5 链的构造

链可以在代码里硬编码，也可以从配置读。

**硬编码。** 简单直接，适合规则固定的小系统。

**配置驱动。** 配置文件里列出链路，每项对应一个处理者。启动时按顺序构造。

```json
{
  "approval_chain": ["leader", "manager", "director", "board"]
}
```

配置驱动的好处是调整顺序不用改代码。坏处是配置错了不容易发现，需要启动时校验：每个名字对应的处理者是否存在，链路是否有环。

责任链一般不应该有环。如果有环，请求可能在里面转圈。构造时应该检查。

## 13.6 什么时候不该用

**只有一两个处理者。** 一个 `if` 就能解决，加一层链反而更绕。

**处理顺序经常变。** 链的顺序是结构的一部分，频繁调整说明规则还不稳定。这时候先用配置加简单的分派，等情况稳定再抽象。

**每个请求都需要所有处理者。** 如果每个环节都要执行，那不是责任链，是管道或者装饰器。

**处理者之间需要共享状态。** 责任链假设处理者相互独立。如果后一环要用前一环的中间结果，应该把它们合成一个处理者，或者改用管道模式。

## 13.7 与装饰器的区别

两者都是“一层层传递”，但语义不同。

**责任链**是“找到能处理的人”。请求通常只被一个处理者处理，处理完就停。

**装饰器**是“每层都做一点事”。请求每层都过，每层都转发。

从代码上看，责任链的处理者可以在某一环返回，不再转发；装饰器几乎总是转发。

## 13.8 与状态模式的区别

**责任链**处理的是“这个请求该由谁处理”，链是静态的，请求在链上移动。

**状态**处理的是“这个对象现在处于什么状态，行为随之改变”，状态会在对象内部切换。

一个具体的区别：责任链的下一环在构造时确定；状态的下一个状态在运行时根据事件决定。

## 13.9 一个判断标准

要不要用责任链，看三点。

第一，有没有一组处理者，每个能处理一部分请求？有，责任链合适。

第二，处理者的顺序和数量会不会变化？会，链能把变化收在构造处。

第三，请求是不是只需要一个处理者？是，纯链；如果需要多个，考虑管道。

三点都成立，责任链合适。
