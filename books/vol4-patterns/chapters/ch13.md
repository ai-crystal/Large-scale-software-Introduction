# 第 13 章 责任链：沿着一条链找处理者

## 13.1 报销审批

公司要做一个报销审批功能。

规则是这样的。金额小于五百，组长审批。五百到五千，部门经理审批。五千到五万，总监审批。超过五万，要走总裁办。

最初的实现是一个函数。

```text
approve(amount):
    if amount < 500:
        return leader.approve(amount)
    else if amount < 5000:
        return manager.approve(amount)
    else if amount < 50000:
        return director.approve(amount)
    else:
        return board.approve(amount)
```

这段代码清楚，但改起来麻烦。

**规则会变。** 公司调整审批额度，要改这个函数。加一个“财务复核”环节，也要改。

**审批人可能缺席。** 经理出差时，应该由代理经理审批。这个逻辑往哪放？塞进 `if` 里，函数会越来越长。

**不同业务线的规则不同。** 销售部的额度比研发部高。如果每个业务线都写一个函数，会有大量重复。

## 13.2 把审批人串成一条链

责任链模式的思路是：每个审批人都是一个处理者，处理者知道自己下一个是谁。请求从链头开始，能处理就处理，不能处理就交给下一个。

它包含三个角色。

**处理者接口。** 声明“处理请求”的方法，以及“设置下一个处理者”的方法。

**具体处理者。** 实现处理逻辑。能处理就返回结果；不能处理就看有没有下一个，有就转发。

**客户端。** 构造链，把请求交给链头。

用结构描述。

```text
interface Approver
  set_next(next) : Approver
  approve(req) : Result

class Leader implements Approver
  next : Approver
  approve(req)
    if req.amount < 500: return Result.approved("组长")
    if next == null: return Result.rejected("无人处理")
    return next.approve(req)

class Manager implements Approver
  approve(req)
    if req.amount < 5000: return Result.approved("经理")
    if next == null: return Result.rejected("无人处理")
    return next.approve(req)
```

## 13.3 协作过程

1. 启动时按规则构造链：组长 → 经理 → 总监 → 总裁办。
2. 客户端把请求交给组长。
3. 组长判断金额，符合自己的额度就批准，返回。
4. 不符合，调用 `next.approve`，请求传给经理。
5. 一直传到能处理的那一环。
6. 如果传到最后都没人处理，返回“无人处理”。

整个过程中，客户端只认识链头，不知道链有多长、每一环是谁。

加一个“财务复核”环节，只需要在构造链时插进去，处理者类不用改。调整额度，只改对应处理者的判断条件。

## 13.4 纯链与不纯链

责任链有两种形态。

**纯链。** 一个请求必须被某一环处理，处理完就停止。如果没人处理，视为失败。审批流是典型的纯链。

**不纯链。** 每一环都可以处理一部分，处理完继续往下传。日志链、过滤器链是典型的不纯链。

不纯链更像装饰器，区别在于：责任链的每一环可以选择“不处理”，装饰器的每一层通常会执行。

写代码时要明确是哪一种。纯链要有“无人处理”的兜底，不纯链要定义“某一环失败后是中断还是继续”。

## 13.5 链的构造

链可以在代码里硬编码，也可以从配置读。

**硬编码。** 简单直接，适合规则固定的小系统。

**配置驱动。** 配置文件里列出链路，每项对应一个处理者。启动时按顺序构造。

```json
{
  "approval_chain": ["leader", "manager", "director", "board"]
}
```

配置驱动的好处是调整顺序不用改代码。坏处是配置错了不容易发现，需要启动时校验：每个名字对应的处理者是否存在，链路是否有环。

```cpp
std::unique_ptr<Approver> build_chain(const std::vector<std::string>& names) {
    std::unique_ptr<Approver> head;
    Approver* tail = nullptr;
    std::set<std::string> seen;
    for (const auto& n : names) {
        if (!seen.insert(n).second) throw ConfigError("重复的处理者 " + n);
        std::unique_ptr<Approver> node = registry().make(n);  // 名字拼错这里就抛
        Approver* raw = node.get();
        if (head) tail->set_next(std::move(node));
        else      head = std::move(node);
        tail = raw;
    }
    if (!head) throw ConfigError("审批链为空");
    return head;
}
```

这个循环把三件事一起做了，查重、查名字、建链。名字存不存在交给注册表，缺了就抛，不用等到第一个请求进来才发现链是断的。

责任链一般不应该有环。如果有环，请求可能在里面转圈。构造时应该检查。

## 13.6 一个 C++ 的审批链

处理者之间用 `unique_ptr` 串起来，链的所有权很清楚，链头活着，整条链就活着。

```cpp
class Approver {
public:
    virtual ~Approver() = default;
    Approver& set_next(std::unique_ptr<Approver> next) {
        next_ = std::move(next);
        return *next_;
    }
    virtual Result approve(const Request& req) const = 0;

protected:
    Result pass(const Request& req) const {
        if (!next_) return Result::rejected("无人处理", req.amount);
        return next_->approve(req);
    }

private:
    std::unique_ptr<Approver> next_;
};

class Leader : public Approver {
public:
    Result approve(const Request& req) const override {
        if (req.amount < 500) return Result::approved("组长", req.amount);
        return pass(req);
    }
};
```

`set_next` 返回下一个处理者的引用，装配就能一行接一行。

```cpp
auto chain = std::make_unique<Leader>();
chain->set_next(std::make_unique<Manager>())
     .set_next(std::make_unique<Director>())
     .set_next(std::make_unique<Board>());
```

`pass` 放在基类里，具体处理者只管自己的条件，“无人处理”的兜底也只写一次。真实系统里兜底往往是一个真对象，比如默认审批人或者转人工，而不是一个空分支，这样链尾不会出现没人接的情况。

`approve` 声明成 `const`，是为了把“链只读”这个约束交给编译器。并发审批时，一条链被多个请求共用，任何一个非 const 的成员变量都可能被踩。

## 13.7 环、短路与异常

三个跟链形态有关的问题，上线前都要想一遍。

**环。** A 的下一环是 B，B 的下一环又指回 A，请求就出不来了。这种错误多出现在配置驱动里，人手动配错了一个名字。构造时用一次颜色标记检测，或者干脆限制跳数，超过链长就报错。

**短路。** 纯链在某环返回后，后面的环永远不执行。如果后面的环里有“记一条审批日志”这种必须执行的动作，它会被跳过。这类必须执行的事不该放在链上，应该放在链外，用一层包装把整条链包住，无论结果如何都记一笔。

**异常。** 某一环抛异常，是中断整条链，还是当成“不处理”继续往下传。两种都有人用，但必须统一。经验上选中断，异常通常意味着系统错误，继续往下传会让错误被后面的环掩盖，日志里只剩一条“审批被驳回”，真正的原因没了。

还有一个容易忽略的细节，处理者可能共享状态。比如经理出差时由代理人顶班，代理人要读经理的额度。这种共享应该用构造参数注入，别让处理者去摸全局单例。

## 13.8 一个偷偷改请求的处理者

有个报销系统在链上加了一个“财务预处理”环节，它把金额里的税额剥离，直接把 `amount` 改成不含税金额。代码只有两行，看起来像是在规范化数据。

上线后出现批量投诉，五千块以上的报销本该总监批，实际却由经理批了。因为预处理把五千二的含税金额改成了四千八，后面的经理看到四千八，符合自己的额度，直接批了。

问题在于，处理者修改了请求本身，后面的环看到的是改过的值，却不知道值被改过。链的语义是传递同一个请求，一旦有人动了它，每一环的判断依据就不再一致。

收拾的方式是把预处理从链里拿出来，放到链之前。如果确实需要传递中间结果，就在请求里加一个显式字段。

```cpp
struct Request {
    int amount;                          // 原始金额，链上任何环都不许改
    std::string category;
    std::optional<int> pre_tax_amount;   // 预处理结果，显式声明，谁都能看到
};
```

判据很简单。处理者可以读请求，可以返回结果，不可以改请求。需要往上传信息时，用返回值或者新建的上下文对象，别在共享的请求上打补丁。

## 13.9 什么时候不该用

**只有一两个处理者。** 一个 `if` 就能解决，加一层链反而更绕。

**处理顺序经常变。** 链的顺序是结构的一部分，频繁调整说明规则还不稳定。这时候先用配置加简单的分派，等情况稳定再抽象。

**每个请求都需要所有处理者。** 如果每个环节都要执行，那不是责任链，是管道或者装饰器。

**处理者之间需要共享状态。** 责任链假设处理者相互独立。如果后一环要用前一环的中间结果，应该把它们合成一个处理者，或者改用管道模式。

## 13.10 与装饰器的区别

两者都是“一层层传递”，但语义不同。

**责任链**是“找到能处理的人”。请求通常只被一个处理者处理，处理完就停。

**装饰器**是“每层都做一点事”。请求每层都过，每层都转发。

从代码上看，责任链的处理者可以在某一环返回，不再转发；装饰器几乎总是转发。

## 13.11 与状态模式的区别

**责任链**处理的是“这个请求该由谁处理”，链是静态的，请求在链上移动。

**状态**处理的是“这个对象现在处于什么状态，行为随之改变”，状态会在对象内部切换。

一个具体的区别：责任链的下一环在构造时确定；状态的下一个状态在运行时根据事件决定。

## 13.12 一个判断标准

要不要用责任链，看三点。

第一，有没有一组处理者，每个能处理一部分请求？有，责任链合适。

第二，处理者的顺序和数量会不会变化？会，链能把变化收在构造处。

第三，请求是不是只需要一个处理者？是，纯链；如果需要多个，考虑管道。

三点都成立，责任链合适。

装配完之后，把这几项逐条核一遍，任何一项出问题都会在线上放大。

| 核查项 | 不通过的表现 |
|---|---|
| 链尾兜底 | 请求走到头返回一个空结果，调用方以为审批通过 |
| 启动校验 | 配置里名字写错，第一个请求进来才发现 |
| 请求只读 | 某一环改了金额，后面几环的判断依据全变 |
| 必须执行的动作 | 被短路跳过，审批日志缺了一条 |
| 链的长度 | 超过五六环，说明这条链在兼管好几件事 |
